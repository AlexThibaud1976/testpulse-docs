TestPulse is **read-only by default**. It reads Test Plans, results and work items to build reports and signals, and it **writes nothing on its own**. Every write in the product follows an **action you trigger yourself**, from a screen that tells you beforehand what it is about to do.

## What "read-only by default" means here

- **No background writes, ever.** Opening a report, a dashboard or the coverage tab changes nothing in your project.
- **Nothing happens without your gesture.** There is no scheduled job, no sync, no silent correction.
- **Nothing is written that a screen did not announce first.** Every write action shows you its scope — and, when it modifies existing data, its exact impact — before you confirm.
- **100% client-side**: reports are built in your browser. **No backend** — no data ever leaves your Azure DevOps tenant.
- The on-work-item signals read **live** and change nothing.

## Two kinds of write action

### Actions that create

These add new objects and never touch what already exists.

- **Coverage Builder** creates Test Plans and requirement-based suites from a set of requirements, behind a confirmation dialog. It never overwrites or deletes, warns on a name collision, and reports partial failures honestly. Scope: `vso.test_write`.
- **Exploratory testing** files a **Bug** or a **Test Case** from what you observed, and closing a session creates a **Task** carrying the whole session — report, captures, files, and links to everything you filed. All created, never modified: TestPulse links the new work item to your story, it does not touch the story itself. Scope: `vso.work_write`.
- **Session closure** can set the state of the tracking Task it just created, if you ask for it in the closing dialog. This write is bounded to that Task, in the same gesture, and never retried. Scope: `vso.work_write`.

### Actions that modify what you selected

One action modifies data that existed before your gesture, because that is precisely what you asked it for.

- **Bulk reassignment** changes the **tester** or the **configuration** of the test points in the scope you defined — a plan, a suite and its children, or one value replaced by another. It is the only place where TestPulse modifies existing test data, it never runs without an explicit confirmation, and it always shows a full impact review first: points affected, suites touched, points already run, cases skipped. Scope: `vso.test_write`.

<Warning>
Bulk reassignment **cannot be undone**. Azure DevOps offers no undo and TestPulse keeps no prior state — a deliberate choice, stated on screen above the apply button. Changing a **configuration** rewrites the test case's assignments, which Azure DevOps may implement by recreating the test point, taking its execution result with it; the review screen says so and lets you exclude points that already carry a result. Export the prior state as CSV before applying if you want a trace.
</Warning>

<Note>Outside that action, TestPulse never modifies or deletes a work item, plan, suite or test case that existed before your gesture.</Note>

## Permission scopes (reference)

| Scope | Why it is requested |
| --- | --- |
| `vso.test` | Read Test Plans, suites, cases, points and results. |
| `vso.work` | Read work items (requirements, bugs) for traceability, and read a work item type's states. |
| `vso.identity` | Resolve testers and assignees by name. |
| `vso.build` | Read the associated build for a report. |
| `vso.test_write` | Create plans and suites from the Coverage Builder, and reassign testers or configurations from Bulk reassignment. |
| `vso.work_write` | Used **only** by exploratory testing: create Bugs, Test Cases and the session Task, upload their attachments, and set that Task's state at closure. |

<Note>Nothing reads comments or personal data beyond what a report needs. See the Permissions page for the full breakdown.</Note>
