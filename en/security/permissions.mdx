TestPulse requests only the scopes it needs. It **never writes on its own**: every write is triggered by an explicit gesture on your part, and each one is bounded to what it creates — or, in two confirmed cases, to exactly what you selected.

| Scope | Read / Write | Why it is requested |
| --- | --- | --- |
| `vso.test` | read | Test Plans, suites, cases, points and results. |
| `vso.work` | read | Work items (requirements, bugs) for traceability, and a work item type's available states. |
| `vso.identity` | read | Resolve testers and assignees by name. |
| `vso.build` | read | The associated build for a report. |
| `vso.test_write` | **write** | Create Test Plans and suites from the Coverage Builder, and reassign testers or configurations from Bulk reassignment. |
| `vso.work_write` | **write** | Exploratory testing only — create Bugs, Test Cases and the session Task, upload their attachments, set that Task's state at closure, and — when you record a promotion decision — add a tag and one discussion comment on the work item the session was run from. |

## The two write scopes

### `vso.test_write` — Coverage Builder and Bulk reassignment

Powers two actions, both triggered by you.

**Coverage Builder — create.** Creates Test Plans and requirement-based suites. Create-only: it never overwrites or deletes an existing plan or suite.

**Bulk reassignment — modify.** Changes the **tester** or the **configuration** of the test points in a scope you defined. This is the only place in the product where TestPulse modifies test data that existed before your gesture, and it is exactly what the action is for. It always shows a full impact review first — points affected, suites touched, points already run, cases skipped — and the apply button stays disabled while the impact is nil.

<Warning>Bulk reassignment cannot be undone: Azure DevOps offers no undo and TestPulse keeps no prior state. Changing a **configuration** rewrites the test case's assignments, which Azure DevOps may implement by recreating the test point, taking its execution result with it. The review screen states this and lets you exclude points that already carry a result; the prior state can be exported as CSV first. See [Read-only by default](/en/concepts/read-only).</Warning>

### `vso.work_write` — exploratory testing

Powers **only** what an exploratory session files at your request: a Bug, a Test Case, the session's tracking Task, and their attachments. All created — TestPulse links a new work item to your story. The only thing it may write back on the story itself is the promotion decision described below.

Two narrow exceptions, both at session closure and both behind the same dialog. The first can set the state of **the Task TestPulse just created**, in the same gesture. The second, when you record a **promotion decision**, adds a tag and one discussion comment on **the work item the session was run from** — one target, two fields, never a state, an assignment or a link; skipped if the form carries unsaved changes, never blocking, and switchable off by an administrator. See [Promotion decision](/en/exploratory/promotion-decision).

<Note>Adding a write scope to the manifest is an **administrator** action and triggers an **extension re-approval** for the organisation. Until then, everything read-only keeps working — only the corresponding create action is unavailable.</Note>

## Permission ≠ scope

A **403** when creating a plan is almost always an **area-path ACL** — the *Manage test plans* permission is granted **per area path** — **not** a missing scope. See [Create the plan in Azure DevOps](/en/coverage-builder/create-plan).
